# چیستی نو در v4

TOON v4 اولین انتشاری است که تودرتو بودن دیگر هزینه خط ندارد. هر مثال در این صفحه همان سند آب‌وهوا را کدگذاری می‌کند.

::: tip شماره‌گذاری نسخه
پکیج `@toon-format/toon` از `2.3.1` مستقیم به `4.0.0` پرید تا با مشخصات هم‌سو شود. وقتی این صفحه «خروجی v3» می‌گوید، منظور خروجی `@toon-format/toon@2.3.1` است.
:::

## مثال

```json
{
  "location": { "city": "Berlin", "country": "DE", "units": "metric" },
  "alerts": ["frost", "wind"],
  "forecast": [
    { "day": "Mon", "temp": { "min": -2, "max": 4 }, "condition": "snow", "rainChance": 80 },
    { "day": "Tue", "temp": { "min": 1, "max": 7 }, "condition": "cloudy", "rainChance": 20 },
    { "day": "Wed", "temp": { "min": 3, "max": 11 }, "condition": "sunny", "rainChance": 5 }
  ],
  "stations": {
    "tempelhof": { "lat": 52.47, "lon": 13.4, "active": true },
    "tegel": { "lat": 52.55, "lon": 13.29, "active": false },
    "dahlem": { "lat": 52.46, "lon": 13.3, "active": true }
  }
}
```

بازفرمت برای خواندن – هر دو ردیف JSON زیر روی خروجی واقعی `JSON.stringify` اندازه‌گیری شده‌اند.

::: code-group

```toon [TOON v4]
location:
  city: Berlin
  country: DE
  units: metric
alerts[2]: frost,wind
forecast[3]{day,temp{min,max},condition,rainChance}:
  Mon,-2,4,snow,80
  Tue,1,7,cloudy,20
  Wed,3,11,sunny,5
stations[3:]{lat,lon,active}:
  tempelhof: 52.47,13.4,true
  tegel: 52.55,13.29,false
  dahlem: 52.46,13.3,true
```

```toon [TOON v3]
location:
  city: Berlin
  country: DE
  units: metric
alerts[2]: frost,wind
forecast[3]:

    temp:
      min: -2
      max: 4
    condition: snow
    rainChance: 80
  - day: Tue
    temp:
      min: 1
      max: 7
    condition: cloudy
    rainChance: 20
  - day: Wed
    temp:
      min: 3
      max: 11
    condition: sunny
    rainChance: 5
stations:
  tempelhof:
    lat: 52.47
    lon: 13.4
    active: true
  tegel:
    lat: 52.55

    active: false

    lat: 52.46
```

:::

| کدگذاری | توکن | خطوط |
| --- | --- | --- |
| JSON، فشرده | 162 | 1 |
| JSON، تورفتگی ۲ فاصله | 301 | 57 |

شمارش با `gpt-tokenizer` روی `o200k_base`.

در این سند، v3 بدتر از JSON فشرده بود. صرفه‌جویی TOON همیشه از سرایند جدول می‌آمد، و v3 آن سرایند را از دست می‌داد هر زمان که یک مقدار شیء بود. هر دو قالب جدولی جدید برای بازیافتن آن وجود دارند.

## گروه‌های فیلد تودرتو

در v3، یک شیء تودرتو کافی بود تا یک آرایه را از قالب جدولی خارج و به تورفتگی برگرداند. `temp` یک شیء است، پس تمام سه ورژن پیش‌بینی هزینه کامل کلید را پرداخت کردند.

v4 به سرایند اجازه می‌دهد تودرتو را توصیف کند: یک فیلد به دنبال یک گروه آکولاد در ستون‌های خودش گسترش می‌یابد:

```diff
- forecast[3]:
-   - day: Mon
-     temp:
-       min: -2
-       max: 4
-     condition: snow
-     rainChance: 80
-   … ۱۲ خط بیشتر برای Tue و Wed
+ forecast[3]{day,temp{min,max},condition,rainChance}:
+   Mon,-2,4,snow,80
+   Tue,1,7,cloudy,20
+   Wed,3,11,sunny,5
```

تنها آرایه forecast از ۱۰۲ توکن به ۴۹ می‌رسد. گروه‌ها به‌صورت بازگشتی عمیق می‌شوند. جایی که گروهی اعمال نشود، خروجی v4 بایت به بایت با v3 مطابقت دارد. قوانین کامل در [نمای کلی قالب](/guide/format-overview#nested-field-groups).

پیشنهاد شده در [spec#46](https://github.com/toon-format/spec/issues/46) توسط [@Turtle-dev3](https://github.com/Turtle-dev3).

## قالب جدولی کلیددار

نصف دیگر مسئله: یک شیء که *مقادیر* آن اشیای یکنواختند. `stations` یک جدول جستجو است، اما v3 آن را یک‌یکی کلید به کلید می‌نوشت.

v4 آن را در جدولی جمع می‌کند که ردیف‌های آن کلیدهای خود را حمل می‌کنند. یک دونقطه مستقیماً بعد از طول – `[3:]` – فرم کلیددار را علامت‌گذاری می‌کند، و لیست فیلدها الزامی است:

```diff
- stations:
-   tempelhof:
-     lat: 52.47
-     lon: 13.4
-     active: true
-   … ۸ خط بیشتر برای tegel و dahlem
+ stations[3:]{lat,lon,active}:
+   tempelhof: 52.47,13.4,true
+   tegel: 52.55,13.29,false
+   dahlem: 52.46,13.3,true
```

۷۶ توکن به ۵۳. نیاز به حداقل دو ورودی دارد، و به فیلدهای شیء و ریشه سند اعمال می‌شود اما هرگز داخل یک ستون. یک سرایند کلیددار می‌تواند گروه‌های فیلد تودرتو حمل کند: `stations[3:]{coords{lat,lon},active}:`. قوانین کامل در [نمای کلی قالب](/guide/format-overview#keyed-tabular-objects).

مشخص شده در [spec#57](https://github.com/toon-format/spec/issues/57)، مبتنی بر پیشنهادهای قبلی از [@cstroliadavis](https://github.com/cstroliadavis) ([spec#32](https://github.com/toon-format/spec/issues/32)) و [@metafishTV](https://github.com/metafishTV) ([spec#45](https://github.com/toon-format/spec/issues/45)).

## کامنت‌ها

خطی که اولین کاراکتر غیرفاصله‌اش `#` باشد یک کامنت است. در یک پیش‌گذر واژگانی حذف می‌شود، در هر دو حالت سخت‌گیرانه و غیرسخت‌گیرانه، بنابراین هرگز یک محدوده را تمام نمی‌کند و هرگز به طول اعلام‌شده اضافه نمی‌شود:

```toon
# صادرات هفتگی، تولید 2026-08-22
forecast[2]{day,condition}:
  # دوشنبه پس از هشدار یخ‌بندان بازبینی شد
  Mon,snow
  Tue,cloudy
```

به دو ردیف رمزگشایی می‌شود. فرم کامنت درون‌خطی یا پیانی وجود ندارد – `#` فقط در ابتدای خط و فقط بعد از فاصله‌ها (نه تب) یک کامنت آغاز می‌کند.

رمزگذارها هرگز کامنت تولید نمی‌کنند، و همیشه رشته‌ای که با `#` آغاز شود را نقل‌قول می‌کنند، بنابراین خروجی رمزگذار هرگز به‌عنوان کامنت خوانده نمی‌شود. به [نمای کلی قالب](/guide/format-overview#comments) مراجعه کنید.

درخواست شده در [spec#1](https://github.com/toon-format/spec/issues/1) توسط [@osjimenez](https://github.com/osjimenez) و [spec#3](https://github.com/toon-format/spec/issues/3)؛ قانون نقل‌قول ناشی از [toon#328](https://github.com/toon-format/toon/issues/328) بود.

## حذف شده: جمع‌کردن کلید (Key Folding)

گزینه‌های رمزگذار `keyFolding` و `flattenDepth` و گزینه رمزگشا `expandPaths` حذف شدند، همراه با پرچم‌های CLI `--key-folding`، `--flatten-depth` و `--expand-paths`. یک کلید نقطه‌دار اکنون بی‌شर्त یک کلید عینی واحد است:

```toon
# v4 این را به‌عنوان یک کلید به نام "data.meta.items" می‌خواند
data.meta.items[2]{id,name}:
```

فقط سندهایی که با جمع‌کردن کلید روشن کدگذاری شده‌اند تحت تأثیر قرار می‌گیرند؛ خروجی پیش‌فرض v3 هرگز از آن استفاده نمی‌کرد. برای مهاجرت سندهای ذخیره‌شده، یک بار با رمزگشای v3 با `expandPaths: "safe"` رمزگشایی کنید، سپس با v4 دوباره کدگذاری کنید.

## همچنین در v4.0

قوانین سمت رمزگشا که نحوه نمایش سند را تغییر نمی‌دهند:

- **دستور liczb عددی هنجاری.** یک توکن بدون نقل‌قول فقط در فرم عدد JSON ساده به عنوان عدد رمزگشایی می‌شود، بنابراین `.5`، `1.`، `+5`، `01`، `Infinity`، `NaN`، `0x10` و `1_000` رشته هستند، و رمزگشاها نباید توکن‌ها را به تجزیه‌کننده میزبان وسیع‌تر بسپارند. در سمت رمزگذاری قانون مشابه باعث می‌شود عددهای شبیه ممیز‌دار مانند `+1` در خروجی نقل‌قول شوند.
- **ایمنی کلید پروتوتایپ.** `__proto__`، `constructor` و `prototype` در هر موقعیت کلید ورودی‌های معمولی هستند، و رمزگشایی نباید مدل شیء میزبان را لمس کند.
- **UTF-8 نامعتبر رد می‌شود.** رمزگشاهای ورودی بایتی در حالت سخت‌گیرانه خطا می‌دهند به‌جای جایگزینی U+FFFD.
- **قانون کلید بدون نقل‌قول شل‌تر.** یک کلید بدون نقل‌قول همه چیز قبل از اولین دونقطه بدون نقل‌قول است، بنابراین رمزگشاهای سخت‌گیرانه اکنون کلیدهایی مثل `foo-bar` و `2key` را می‌پذیرند.

## ارتقا

سه مورد را به این ترتیب بررسی کنید:

1. **ابتدا رمزگشاها را به‌روز کنید، بعد رمزگذارها.** گروه‌های فیلد تودرتو روی رمزگشای v3 در هر دو حالت با خطا مواجه می‌شوند. خروجی جدولی کلیددار خطرناک‌تر است: یک رمزگشای سخت‌گیرانه v3 به‌صورت تمیز خطا می‌دهد، اما یک رمزگشای غیرسخت‌گیرانه v3 به‌صورت *ساکت* نادرست رمزگشایی می‌کند.
2. **اسناد ذخیره‌شده v3 را برای `/^ *#/` و سطح‌های تورفتگی ردشده اسکن کنید.** کامنت‌ها تنها تغییر v4 هستند که معنای رمزگشایی خروجی v3 معتبر دیگر را تغییر می‌دهند: یک خط با پیشوند `#` اکنون به‌عنوان کامنت خوانده می‌شود. یک اسکالر ریشه با پیشوند `#` به‌صورت ساکت ناپدید می‌شود؛ داخل یک آرایه جدولی تعداد ردیف‌ها دیگر هم‌راستا نیست، پس خطا می‌گیرید. رفع هر دو: با v4 دوباره کدگذاری کنید، که رشته را نقل‌قول می‌کند و در هر دو نسخه یکسان رمزگشایی می‌شود. جداگانه، سندی که یک سطح تورفتگی را رد می‌کند اکنون خطای حالت سخت‌گیرانه است – فقط فایل‌های دست‌نویس، چون هیچ رمزگذاری هرگز چنین چیزی تولید نکرده.
3. **گزینه‌های حذف‌شده** را از فراخوانی رمزگذار و رمزگشا و از فراخوانی‌های CLI حذف کنید.

## v4.1

تغییر نحوی وجود ندارد، و خروجی `@toon-format/toon` بایت به بایت در v4.0 و v4.1 یکسان است.

چه تغییر کرده است آنچه که مشخصات *نیاز* دارد از یک رمزگذار، که اگر پیاده‌سازی خودتان را نگه می‌دارید مهم است. قالب جدولی اکنون در هر جایی که تشخیص موفقیت‌آمیز باشد و موقعیت اجازه سرایند حامل فیلدها را بدهد، اجباری است، و آرایه‌های خالی باید به‌صورت `key: []` نوشته شوند، هرگز قالب قدیمی `key[0]:`. رمزگشاها همچنان هر آنچه رمزگذار v4.0 می‌توانست تولید کند را می‌پذیرند.

**API جدید.** `rawString()` یک مقدار را علامت‌گذاری می‌کند تا از یک replacer به‌صورت عینی صادر شود، دور از نقل‌قول و تشخیص عدد؛ `escapeString()` اکنون صادر می‌شود. به [مرجع API](/reference/api) مراجعه کنید. مشارکت [@yilmazhasan](https://github.com/yilmazhasan) در [toon#321](https://github.com/toon-format/toon/pull/321).

**گزینه‌ها.** `indentSize` در هر دو `EncodeOptions` و `DecodeOptions` پذیرفته می‌شود؛ `indent` همچنان کار می‌کند اما منسوخ است.

علاوه بر این، v4.1 کار انطباق است: شرایط خطای بی‌بیان صریح شده، مدیریت BOM مشخص شده، و مجموعه‌ای از تغییر نام بخش‌ها در مشخصات.
